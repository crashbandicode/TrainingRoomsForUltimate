## Cross-area notes

- The boot spec lists every `offsets.rs` needle with its 13.0.5 offset, including the ones whose behaviour belongs to SPEC-cpu-* / SPEC-state-* / SPEC-input-* (`cloud_add_limit`, `add_damage`, `training_reset_check`, `stale`/`stale_menu`, `play_se`, `can_futtobi_back`, `reused_ui`, `fim`, `sss_training`, `kirby_opff`, `activate_autonomy`, `pokemon_decide`, `copy_setup`, `set_cpu_controls`, `change_active_camera`, `set_training_fixed_camera_values`, `opcf`, `is_visible_backshield`, `get_battle_object_from_id`, the two fighter vtable slots). Those specs should cite SPEC-core-01 §4.2 rather than repeat the addresses.
- The Infinite-shield parameter rewrite lives in the hitbox `ATTACK` hook upstream (SPEC-core-06 Q2); SPEC-cpu-* (shield) should own it.
- `077a8e43` also gates the L+R+A reset check with `!is_training_mode()` (sign looks inverted; SPEC-core-01 Q3 for SPEC-state-*).
- The notification panel draw (`display.rs`) and input log are SPEC-input-*; SPEC-core-05 owns how the native combo-display setting is read and when the panels are hidden.
- Operator update 2026-11-01 (lead): the standalone CPU pilot plugin has its own menu page, so the menu model (SPEC-core-02) must not carry the fork's P1 CPU Control / Level rows as ordinary rows. They become a conditionally visible group (shown only when the install detects no `libssbu_cpu_pilot`), and with the pilot present a read-only `info` row points at the pilot's page. The model therefore needs row visibility driven by an install-time fact (`standalone_pilot_present`), in addition to the per-scene hiding the fork already does. See `MENU-DRAFT.md` §2/§3 and open question 11.
