# rc.5 grouped Eden session: the rows (card 10a)

`rows.json` is the rc.5 grouped Eden session the recording-redesign slices (rr-1 … rr-9) built:
the rows the stage-1 report's Eden column named, the rc.5 frame-advantage cases and the heap/crash
gates from `artifacts/phase23/EDEN-SESSION-PLAN-rc5.md`, and every GIF `docs/MEDIA.md` still needs.
It was generated by `make_rows.py` from that plan; regenerate with
`/usr/bin/python3 -I eden/recording-redesign/make_rows.py` from the repository root.

- **Shapes copied from the worked examples** (`eden/phase23/rows-iv`, `rows-hb-ab`, `rows-A`):
  every row is one project step hook (`{"run": "steps.py:<row>", "check": true}`, the rows-iv
  shape); every non-library segment is a **recipe** the runner records on its first play
  (playbook `docs/MACROS.md`, "Test runs": recipe inputs are the only single inputs the runner
  ever sends — no `.edenmacro.json` is written by hand, and no segment carries a sha256 before it
  has been recorded); the boot route reuses the proven library segments (`attract-cancel`,
  `main-stage`, `stage-css`, `enter-training`) and gates (`installed`, `main`, `stage`, `css`,
  `ready`, `training-hud-unpaused`, from `tools/eden-runner/library/index.json`).
- **The screen chain is one label thread.** The runner checks it linearly across the whole grouped
  session. The first row (`rr-migrate`) boots instance surface-b (`boot` → `training`); after that every
  row runs at Training, and each later group's first row is a `setup-<instance>` row that
  re-establishes **its own** instance at Training (the `installed` gate, then `steps.py:boot_training`).
  A row's `start`/`end` describe the screen state on that row's instance.
- **Confirming re-run (Surface 2 + Yoga 2).** `surface-a` and `yoga-a` load the release NRO.
  `surface-b` and `yoga-b` load the diag NRO of the same commit. Ally and XPS never reached Training
  in the first pass (stick cursor, then the XPS HUD crop on the fighter tip), so their rows run here.
  Each row's `build` field says which NRO. `heap-and-crash-check` runs on all four.
- **Character select is L3 + D-pad.** `boot_training` walks up to the edge, then left to the edge,
  and requires `settled screen=css at=0 hovered=0` before one A (`docs/TILE-CURSOR.md`; the route
  `rc5-surface-1` recover-enter-training-b and `rc5-xps-04` both settled). The analog stick does not
  move this cursor. One A on tile 0 readies the match while the CPU coin is still Random: Yoga's
  `settings.json` `player_character` / `cpu_character` did not override that coin, and a second A
  cannot pick it up once READY is open. The re-run does not claim the CPU is Mario. A fresh profile's
  fighter tip is one more A, then the HUD gate again. `enter-training` is played from its library
  file; its `ready` start gate is the animated banner and is not used.
- **CPU Shield** for the on-shield advantage rows is the menu route in `docs/MEDIA.md`. The CPU page
  opens on Reactions. Groups are Reactions, Defence, Ledge & Tech, Shield (`src/model/menu/table.rs`).
  Three ZL+Down jumps land on `shield_state`. Options are None, Infinite, Hold, Constant
  (`src/model/menu/options.rs`); factory index 0 is None (`src/model/factory.rs`). Right twice selects
  Hold. A is not pressed (it opens the list). Mash stays the factory empty `mash_state`, so the
  on-hit row does not mash. The diag line is `[FrameStrip] advantage value=N on_shield=true` or
  `on_shield=false` (`src/runtime/features/input_display.rs`, `#[cfg(feature = "diag")]`). That
  function returns `()`, so these rows stay on the diag build. There is no release trace of the readout.
- **Heap.** `heap_crash` reads `events.log` beside `practice-diagnostics.log` and requires the line
  `plugin=training_rooms/… result=installed heap_allocations=0`. The later `cpu_common=installed`
  line has no heap count. The same check runs on the diag instances.
- **Trace arming (release).** `tr_combo_link_v1` and `tr_combo_attempt_v1` (`src/runtime/features/combo.rs`,
  `#[no_mangle]`, not cfg(diag)): `on_return`, and entry captures so the re-run can read the flags.
  Link args are index, link, flags, offset; flags bit 0 true, bit 1 clean, bit 2 wrong move, bit 3
  missing. Attempt args are outcome (1 completed, 2 stopped, 3 cleared), true_links, total, first_bad.
  `f9-body-trace` is a placeholder: `artifacts/phase23/LANE-GROK-RC5-FIX-F9-REPORT.md` was not present.
  Arm `f9_body_of` with `on_return` and captures of `entry`, `[entry+0x4160]`, the state word, and
  `slot` (`artifacts/phase23/TASK-GROK-rc5-fix-f9.md`). The row waits for that return.
- **Image gates** `main`, `stage`, `css`, `ready`, and `training-hud-unpaused` set `"scale": "fit"`.
  The reference ROIs stay 1280×674 and the tolerances stay 8. A full-window grab is 1280×720.
- **Timed rows** stay on the Surface and the Yoga.
- **The shared start** for the in-match rows (from `docs/MEDIA.md`): Training mode, Battlefield,
  both fighters at 0%, P1 Mario and CPU Mario, Input Display = Frame strip, Hitbox Visualization
  Off, CPU Shield = None and DI/SDI cleared unless the row changes one of them, menu closed, chords
  at their factory defaults (Save ZL+Down, Load ZL+Up, Record ZR+Down, Play on Player 1 ZR+Left,
  Play on CPU ZR+Up, Recording pop-up ZR+Right).
- **Evidence:** each hook writes its row folder's evidence (`<row>.json`, screenshots, GIFs) and
  raises with the captured data when its expected observation is missing; the GIF rows record with
  Eden's own recorder (1280 wide, game speed, the documented length).
- **Runtime diag lines and tracepoints (card 10c).** Every runtime row (`rr-migrate`, `rr-record`,
  `rr-notice`, `rr-mismatch`, `rr-rename`, `rr-crop`, `rr-play`, `rr-mash`, `rr-combo`) gates on or
  expects the exact diag line RR-7's Eden rows table gives it (`screen=recording …`,
  `screen=playback …`, `screen=notice kind=…`, `screen=mismatch ask=macro1`, `screen=rename …`,
  `screen=crop …`, `screen=migrate once=1`): the row's hook waits for the line and raises without
  it, and where the line is a hard expectation the row also carries a **log gate on the diag
  source** (`{"gate": "diag-…"}`, `kind: log`, `source: diag`) after the hook — the runner scopes
  log gates to the row's own lines. `rr-combo` has no gate: RR-7 says the Connections panel line is
  the published frame, not a diag print. Each runtime row also carries RR-7's **tracepoint** as a
  `trace` note; RR-7 names functions only (no addresses), so nothing is armed in the plan — the
  session resolves the symbol after `symbols.load` (Open questions).

## Recovery and start gates (card 10b)

Playbook `docs/MACROS.md`, "Test runs" (rule 8): a run continues past a failed row only when the
next row has a start gate and a recover list; the runner then plays the list and checks the start
gate, and stops (`STOP-INPUT`) only when recovery itself fails or the game is gone. Every row after
`rr-migrate` (the session's first row, which boots surface-b) carries
`"start_gate": "training-hud-unpaused"` — the library gate that proves the row's `start` screen
(Training, HUD unpaused). The plan carries one `recover` list for all of them, because they all
start at the same screen: the `menu-close` recipe (B closes the menu; a second B closes the pop-up
— with both already closed the fighter's special plays, and the Load after it undoes that), then
the `chord-load` recipe (ZL+Up warps both fighters to the bound save and starts nothing, RR-4 A5),
and nothing else. The `setup-<instance>` rows start somewhere else — their own instance, not a
match screen — so each carries its own recover list instead: `steps.py:boot_training` on that
instance (game.load when it has not loaded, the library route, the HUD gate), the same hook its
steps run.

## The rows

### rr-migrate (surface-b, diag, first row)

- **Start state:** a fresh plugin index and one live legacy recording slot (fixture pinned before
  boot); the game boots on the release NRO with all slices merged.
- **What it does:** boots; the worker calls the migration once at its tick.
- **What passes it:** the diag line `screen=migrate once=1`; the migrated macro is named
  `Slot N (YYYY-MM-DD)` with the boot date; a second tick does not rewrite the tree.
- **Source:** RR-7, "Eden rows for rr-10", row `rr-migrate`; stage-1 report clause A13 and the
  migration table.
- **Tracepoint (RR-7):** `migrate_at_boot` — capture the slot name containing the boot date; a
  second tick does not rewrite the tree.

### media-rc5-migration (xps-a)

- **Start state:** right after `rr-migrate` on the same boot; nothing else set active.
- **What it does:** plays the migrated slot (`Slot 1 (date)`) on camera.
- **What passes it:** the name uses `Slot 1` and the date; play does not warp (no `playback … warp=1`
  line); empty slots did not become files.
- **Media:** `media/rc5-migration.gif`, 8 s.

### rr-record (xps-a)

- **Start state:** Training match, pop-up role Player, not recording.
- **What it does:** ZR+Down starts the recording (one jab on camera), the pop-up role moves to CPU,
  ZR+Down again stops it.
- **What passes it:** `screen=recording role=player recording=1`, then
  `screen=recording role=cpu recording=0`; the macro is written only when frames were stored.
- **Source:** RR-7, "Eden rows for rr-10", rows `rr-record`; stage-1 report line 166.
- **Tracepoint (RR-7):** `recording_host::on_chords` when the record bit is set — capture the
  capture role and whether recording is on; the stop wrote the macro only when frames were stored.

### rr-notice (xps-a)

- **Start state:** Training; a recorded macro with a start save.
- **What it does:** plays a macro after the boot's first chords (the chord-once notice), then
  deletes the macro's start save through its own screen (the plugin menu's Delete removes the file)
  and plays the macro again.
- **What passes it:** `screen=notice kind=chord-once` once after boot;
  `screen=notice kind=macro-start-save-missing` only for the deleted start-save file.
- **Source:** RR-7, "Eden rows for rr-10", rows `rr-notice`; stage-1 report clause A15.
- **Tracepoint (RR-7):** `start_save_notice` for `Deleted` — a missing id with the switch off does
  not print the line; the chord-once flag is read and set by the worker, a second chord does not
  print it.

### rr-mismatch (xps-a)

- **Start state:** a chain whose macro 1's fighter differs from the current P1 (and macro 2 as well).
- **What it does:** plays the chain on the CPU; the Fighter Mismatch prompt appears once at the
  chain's start; the hook answers **Keep** (the GIF's choice).
- **What passes it:** `screen=mismatch ask=macro1`; the prompt names macro 1's fighter; no second
  prompt when the later macro plays.
- **Source:** RR-7, "Eden rows for rr-10", row `rr-mismatch`; stage-1 report line 326.
- **Tracepoint (RR-7):** `chain_mismatch` — capture step 0 only, and that Switch names macro 1's
  fighter.

### rr-rename (xps-a)

- **Start state:** a macro file screen, cursor on Rename; Online is off.
- **What it does:** A, then the keyboard offer appears; B leaves it without renaming.
- **What passes it:** `screen=rename header=Name macro`; with Online on the offer is not made

- **Source:** RR-7, "Eden rows for rr-10", row `rr-rename`.
- **Tracepoint (RR-7):** `Effect::Keyboard`, then the titled keyboard offer; online captures the

### rr-crop (xps-a)

- **Start state:** a macro with the replay window handles inside the tape.
- **What it does:** A on Crop; the crop screen opens; B leaves it.

### rr-load (xps-a)

- **Start state:** both fighters standing; a bound save.

  between them; the inner macros' start saves are not used.

### rr-play (xps-a)

- **Start state:** Player 1's active macro has a start save with the switch on (case 1); then the
  CPU's active macro has no start save (case 2). Which macro sits under the pop-up cursor when the

- **What it does:** Play on Player 1 (ZR+Left, `[7,10]`); the loop passes play out; then Play on
  CPU (ZR+Up, the old Input Playback chord).
- **What passes it:** `screen=playback role=player warp=1` with the warps count staying 1 across

  `warps` staying 1 across the loop; the CPU case is the same drain with `Role::Cpu`, no warp.

## Open questions

Facts the card's sources did not give. Each row still runs with what its source gives; the session
fills or corrects these.

1. **The published frame-data pages (`adv-*` rows).** `EDEN-SESSION-PLAN-rc5.md` requires citing
   the published source page and its version and quoting its number, but no source file this card
   names contains a page, a version or a number. The rows carry
   `published: to be filled by the session` and no frame number is invented.
2. **The hook-stats snapshot line format.** The plan names the snapshot (`src/model/hook_stats.rs`)
   but no file gives its diag line format; `steps.py:hook_stats` copies the `hook_stats` diag lines
   into the row folder and fails on a nonzero steady-state allocation counter read from the line.
3. **Menu cursor routes inside the new screens.** The reports give the buttons each screen takes
   (A, B, X, L/R, ZL/ZR, ZL+Up/Down paging) but not how many presses reach a given row (Rename,
   Crop, Delete, Make combo, Shield → Hold). The hooks walk the documented direction bounded and
   screenshot every stop; the session tunes the counts.
4. **The CSS tile for Mario/Mario.** The boot hook hovers until the tile cursor settles and
   confirms both roles; the exact tile number for Mario is not in any named source.
5. **The recipes' frame counts are not measured timings.** The chord recipes hold the factory
   button pairs (RR-5's table) for a short frames-based hold; the movement and combo recipes use
   the thresholds rr-12 measured in the stock 13.0.5 params (dash_stick_x 0.85, dive_cont_value
   −0.66, jump_stick_y 0.7), but every hold/gap frame count is the recipe's best effort for the
   described behaviour. Each recipe carries `"note": "timing to be checked when recorded"`; the
   runner writes back each segment's sha256 when it records it, and the session corrects the
   recipe from the take.
6. **The C-stick cannot be expressed by a recipe.** The runner's recipe actions drive the left
   stick only (`record()`'s stick action), so the `cstick-smash` segment's recipe is a placeholder
   that must not be played as-is (its `note` says so). The `strip-cstick-smash` and
   `media-rc5-frame-strip-cstick` hooks press the right stick directly with a bounded
   `input.stick` call and capture the answer; no run's `actions.jsonl` in this workspace shows a
   right-stick call, so whether the control API accepts one is unverified. If it refuses, the
   session records the C-stick take by hand (MACROS, "one bounded recording") or the recipe syntax
   gains a right-stick action.
7. **`rr-notice`'s chord-once case.** The boot route itself presses chords before the row, so the
   first chord after boot has already happened by the time the row runs; the hook records whether
   the `chord-once` line is still available in this boot and the session orders the row first after
   boot if it must be observed fresh.
8. **`rr-record`'s pop-up role change mid-recording.** RR-7's two `rr-record` rows are start states
   on separate rows; this card has one `rr-record` row, so the hook performs both presses in one
   row and captures both diag lines.
